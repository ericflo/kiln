# Hypothesis: h1-r16-6ep-tok256

## Family
H1 — epoch curve / rollout budget variant (same hyperparams as iter 1
except max_tokens during rollout).

## Claim
Doubling rollout max_tokens (128 → 256) will lift `entity_recall` by
≥3pp (0.6764 → ≥0.7064) without losing the composite gain from iter 1
(stay above 0.83). If iter 1's confound was that the 128-token rollout
budget can ONLY produce length-compressed compactions, doubling the
budget gives OPD room to learn entity inclusion.

## Mechanism
Pruning analysis just showed that with max_tokens=128 the BASE student
already gets length_band=0.93 average — meaning OPD's only marginal
lift on length_band came from confidently keeping responses short. But
entity_recall = 0.78 average on the same rollouts; the base regularly
drops entities in the limited token budget. With 256 tokens, the
student has room to include more entities, so the teacher's distribution
preference for entity-mention tokens has somewhere to land in the
rollout trace. If the diagnosis holds, OPD will now lift entity_recall.

## Configuration
- prompts: prompts/h1-r16-6ep-tok256.jsonl (copy of iter 1's set, 26 prompts)
- rank: 16  alpha: 32  lr: 1e-4
- epochs: 6  samples_per_prompt: 1  max_tokens: 256  top_k: 8
- env: KILN_STREAMING_PREFILL=1
- env: KILN_OPD_USE_CHAT_TEMPLATE_RENDER unset (legacy path)

## What's held constant from previous iteration
EVERYTHING except `max_tokens` (128 → 256). Same prompts, same rank/lr/
epochs/spp/top_k. Single-knob change to isolate the effect of rollout
budget on entity-recall uplift.

## Falsification plan
- If entity_recall Δ < +1pp AND length_band stayed up: diagnosis was
  wrong — OPD's lift wasn't a confound, it just doesn't move
  entity_recall on this trainer. Pivot to H6 (SFT cold-start) next.
- If entity_recall Δ ≥ +3pp: diagnosis confirmed. Iter 3 = H1 with
  max_tokens=256 AND 12 epochs to push further.
- If composite < 0.5 × baseline (< 0.405): all-zeros gate fires;
  treat as broken adapter, write failure_mode.md.
- If skip_rate climbs (was 95%; if it hits 99%+) the longer rollouts
  may have triggered another structural issue; investigate.

## Inspection plan
Sample 3 non-eval responses on train.opd entries 0, 5, 10 after training.
Check whether the compactions are LONGER than iter 1's (target: 80–150
words instead of iter 1's apparent 30–60 words) and whether they
mention more file paths / identifiers.

## Verdict
✓ Confirmed — entity_recall +3.46pp vs baseline (0.6764 → 0.7110, claim
was ≥+3pp). Composite +5.34pp vs baseline (0.8098 → 0.8632) and +2.17pp
vs iter 1 (0.8415). Critically, the lift this time landed on the
TARGET sub-score, not on length compression: entity_recall actually
moved (+3.46pp vs flat -0.39pp in iter 1), and length_band slightly
dropped from iter 1's 0.9708 to 0.9483 (i.e. responses are slightly
longer because the model has room to include entities). Diagnosis
confirmed: with max_tokens=128 the OPD rollout could only learn
length compression as the lowest-cost loss reduction; doubling to 256
gave the gradient somewhere to land on the actual capability gap.

Sub-scores (iter 0 → iter 1 → iter 2):
- entity_recall: 0.6764 → 0.6725 (-0.4pp) → 0.7110 (+3.85pp from iter 1)
- entity_grounding: 0.9606 → 0.9773 → 0.9859 (monotonic)
- length_band: 0.6739 → 0.9708 → 0.9483
- decision_retention: 1.0 → 0.8916 → 0.9386 (regression smaller than iter 1)

Regressions vs baseline: decision_retention -6.14pp (minor — was already
saturated at baseline so any movement is a loss; smaller than iter 1's -10.84pp).

Next: Iter 3 should H1-bump epochs (6 → 12) at max_tokens=256 to test if
entity_recall keeps climbing or has plateaued. If entity_recall Δ vs
iter 2 < +1pp, the curve has saturated; pivot to H2 (prompt diversity)
or close the capability at this composite (+5.3% lift, 28% headroom
utilization).
