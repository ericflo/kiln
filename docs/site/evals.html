Evals · a peer of training

Score every adapter you ship — entirely on your own GPU.

Kiln treats evals as a peer of training, not an afterthought. Pluggable scorers, dataset → suite synthesis, head-to-head adapter comparisons, and post-training auto-grading run on the same single-GPU binary that serves traffic. The optional LLM judge is itself a local LoRA you train from A/B preferences — no frontier-model call is ever required.

Where things live

Two crates, three on-disk stores

The eval system splits into kiln-eval (pure-CPU types: suites, scorers, results, dataset synthesis) and kiln-server::eval (queue, worker, registries, HTTP surface). Suites, datasets, and judgments persist under <eval-root>/{suites,datasets,judgments}/ (configurable via [eval] root). The eval worker rides the GPU read-lock so it runs concurrently with serving and training. The full type and request reference is in EVAL_GUIDE.md; the queue/worker deep-dive is in Architecture › Eval pipeline.

Scorers

Pluggable scorers, registered by kind

Scorers are variants of the serde-tagged kiln_eval::scorers::Scorer enum — each variant computes a 0/1 outcome from (generated, target, metadata), and the kind field on the wire selects which one runs. Built-ins cover the common shapes; adding one means appending a variant, dispatching it in score_completion, and adding a kind_label arm. Synthesis and the UI pick it up automatically.

exact_match — single-source-of-truth answers (math, classification, structured labels).
contains · regex — free-text key-phrase or pattern matching.
json_validity · multiple_choice · numeric_tolerance — structured outputs and graded numeric responses.
tool_call — selected tool + arg shape + per-arg inner-content quality (works for trajectories that end in a tool call).
code with bash introspection — code-output evals, including python -c/node -e/uv run inlined inside bash.
llm_judge — route grading through a local judge LoRA (see the flywheel).
All · Any composites — combine scorers per example for weighted-vote grading.

Auto-detect picks a scorer from the target shape (JSON → JsonValidity + structural checks, short literal → ExactMatch, code block → Code, free text → Contains/LlmJudge).

Dataset → suite

Turn an SFT or GRPO file into a graded suite

Upload one corpus and Kiln persists content-addressed, group-aware train, validation, and holdout views. Named training defaults to train; synthesis defaults to holdout. The training rows never become a held-out grader merely because they came from the same JSONL. Reservoir-sampled max_examples caps keep suites runnable in seconds even on hundreds of thousands of rows.

1. Upload a JSONL dataset

curl -s http://localhost:8420/v1/eval/datasets/upload \
  -F "file=@/tmp/sft-trajectories.jsonl" \
  -F "name=trajectories-v1" \
  -F "format=sft_chat" \
  | python3 -m json.tool

2. Synthesize a suite

curl -s http://localhost:8420/v1/eval/datasets/trajectories-v1/synthesize \
  -H "Content-Type: application/json" \
  -d '{
    "suite_name": "trajectories-suite",
    "source_split": "holdout",
    "strategy": "tool_call_predict",
    "scorer": {"kind": "auto_detect"},
    "sampling": {"max_examples": 256}
  }' \
  | python3 -m json.tool

Strategies

  • final_assistant — grade the last assistant turn.
  • first_assistant_turn — grade the model's opening reply.
  • every_assistant_turn — one example per assistant turn (multi-turn rollouts).
  • tool_call_predict — predict {tool_name, args} for trajectories ending in a tool call.

Inner-content quality

For tool_call_predict, string args carry sub-scorers: prose can be graded by Contains/LlmJudge; code by Code; bash calls are introspected to detect inlined python -c/node -e/uv run blocks and graded as code instead of strings.

The persisted split manifest keeps normalized duplicates and declared groups/sessions together. Inspect or replace it through GET/PUT /v1/eval/datasets/{name}/split. The complete identity, migration, contamination, and provenance contract is in Dataset Splits and Train/Eval Separation.

Run a suite

Grade an adapter against a registered or inline suite

POST /v1/eval/run queues the job and returns immediately with a job_id and exact effective_seed. The eval worker resolves the suite from disk (or uses an inline copy), drives the in-process inference path through the requested adapter, and writes per-example outcomes plus a headline accuracy as it goes. Drill into /ui › Evals to watch progress and copy the job or per-completion seeds.

Admission also snapshots the resident kiln.base-weight-shards.v1 manifest and startup-owned kiln.execution-provenance.v1 record. Job detail and raw JSON retain every shard plus the complete backend/device, runtime, executable/source, model/tokenizer/template, precision, kernel, and effective-configuration envelope. The dashboard and kiln-eval show compact exact-copy summaries; downloaded outcome JSONL carries both complete records on every standalone row, and terminal archives validate them again on restart. See the base-weight and execution provenance contracts.

Run a registered suite against an adapter

curl -s http://localhost:8420/v1/eval/run \
  -H "Content-Type: application/json" \
  -d '{
    "suite": "trajectories-suite",
    "adapter": "my-coder-v3",
    "seed": 42
  }' \
  | python3 -m json.tool

Poll the job

curl -s http://localhost:8420/v1/eval/jobs/$JOB_ID | python3 -m json.tool

Re-run only failures from a completed job with POST /v1/eval/jobs/{id}/rerun. The re-run retains the original effective seed by default; send {"seed": 73} only when changing it deliberately.

Compare

Head-to-head adapter comparison

POST /v1/eval/compare materializes one job seed, derives stable seeds from each example_id and completion index, and runs every adapter on those same sampling inputs. Empty or duplicate resolved example IDs are rejected so seeds and aggregate rows cannot alias. Pass an empty string for one adapter entry to compare against the no-adapter baseline. Omit seed for a recorded random value or set it at the top level without replacing the suite's other generation settings.

Compare three adapters + baseline

curl -s http://localhost:8420/v1/eval/compare \
  -H "Content-Type: application/json" \
  -d '{
    "suite": "trajectories-suite",
    "adapters": ["", "my-coder-v2", "my-coder-v3", "my-coder-v4"],
    "seed": 42,
    "generation": { "temperature": 0.0, "max_tokens": 256 }
  }' \
  | python3 -m json.tool

Results encode effective_seed and each outcome's generation_seed as decimal strings so browser clients preserve all 64 bits. seed_derivation: "kiln.eval-seed.v1" versions the mapping. Seeded inputs support same-environment comparison and audit; they do not imply byte-identical output across different model revisions, binaries, drivers, devices, kernels, or precision policies.

Post-training auto-eval

Grade training against declared held-out data

An SFT or GRPO request can carry a post_eval block whose data_scope defaults to held-out. Before publishing the training job, Kiln rejects exact, normalized, source-row, group, or session overlap with the admitted corpus. After training, it queues the adapter eval and optional baseline comparison and links both from training detail.

SFT request with auto-eval

curl -s http://localhost:8420/v1/train/sft \
  -H "Content-Type: application/json" \
  -d '{
    "dataset": "trajectories-v1",
    "dataset_split": "train",
    "config": { "output_name": "my-coder-v4" },
    "post_eval": {
      "suite": "trajectories-suite",
      "data_scope": "held-out",
      "include_baseline": true,
      "generation": { "temperature": 0.0, "max_tokens": 256, "seed": 42 }
    }
  }' \
  | python3 -m json.tool

The same post_eval shape is supported on /v1/train/grpo. Intentional training-data measurement must use data_scope: "train-set-eval"; that diagnostic label cannot be combined with min_accuracy. See Dataset Splits and Train/Eval Separation and the generated control-plane schema for the full contract.

Judgment flywheel

A/B preferences → SFT → judge LoRA

The flywheel turns human A/B/Tie/Skip preferences into a local judge LoRA you can drop into any future suite as an llm_judge scorer. The keyboard-driven A/B compare playground at /ui › Judgments writes every pick to a JudgmentStore; one curl compiles the picks into an SFT dataset and another trains the judge — all on the same GPU.

POST /v1/judgments — create a judgment dataset.
POST /v1/judgments/{name}/rows — append one A/B/Tie/Skip preference (the /ui playground does this on every pick).
POST /v1/judgments/{name}/compile — compile preferences into an SFT JSONL ready for /v1/train/sft.
POST /v1/judgments/{name}/validate — score the trained judge LoRA against a held-out slice.

Use the trained judge in a suite

{
  "name": "code-quality-suite",
  "examples": [...],
  "default_scorer": {
    "kind": "llm_judge",
    "judge_adapter": "my-judge-v1",
    "template": "Question: {question}\nAnswer: {answer}\nScore 1 if the answer correctly solves the question, else 0.\nScore:"
  }
}

The judge LoRA is hot-swapped exactly like any other adapter, so the eval worker resolves it through the same scheduler that serves your inference traffic.

CLI

kiln-eval CLI

The kiln-eval binary wraps the HTTP surface for scripted use: list, register a suite JSON, run a suite against an adapter (with --watch), compare multiple adapters head-to-head, and probe with a one-shot prompt+target+scorer. Synthesis stays HTTP-only — call POST /v1/eval/datasets/<name>/synthesize. See the CLI Reference and EVAL_GUIDE.md.

Run a suite from the terminal

kiln-eval run --suite trajectories-suite --adapter my-coder-v3
