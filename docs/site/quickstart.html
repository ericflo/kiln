Quickstart · 5-minute path · Qwen3.5-4B

Install Kiln, start the server, point your agent at it.

Three steps to a coding agent backed by your own GPU: install Kiln, start the server, then connect pi or opencode to one local endpoint. Every request your agent makes becomes training data. Every path serves the same target model: Qwen/Qwen3.5-4B.

Prerequisites + choose one path

Install Kiln

Desktop App · recommended

Download Kiln Desktop v0.2.16, then choose or download the Qwen3.5-4B model in the app and start the server from the GUI.

Platform Installer
macOS Apple Silicon .dmg · latest release
Windows .exe (NSIS) / .msi · latest release
Linux .deb / .AppImage · latest release

Desktop and server release lines intentionally differ: the Desktop app ships under desktop-v* tags, downloads and verifies the latest kiln-v* server binary for you, and the links above always resolve to the newest release.

Model path + start

Start the server

a. Download Qwen3.5-4B

Point KILN_MODEL_PATH at a local checkout of Qwen/Qwen3.5-4B.

pip install -U huggingface_hub
hf download Qwen/Qwen3.5-4B --local-dir ./Qwen3.5-4B
export KILN_MODEL_PATH=./Qwen3.5-4B

b. Run the server with kiln serve

Server binaries bind to 127.0.0.1:8420 by default. No API key required.

KILN_MODEL_PATH=./Qwen3.5-4B ./kiln serve

Docker (Linux + NVIDIA Container Toolkit)

docker run --gpus all -p 8420:8420 \
  -e KILN_MODEL_PATH=/models/Qwen3.5-4B \
  -v "$PWD/Qwen3.5-4B:/models/Qwen3.5-4B:ro" \
  ghcr.io/ericflo/kiln-server:latest serve
3

The #1 thing to do with Kiln

Connect your agent

Point pi or opencode at the server you just started. There is no SDK to swap and no key to generate — change the base URL and keep your agent. Every request it makes streams into /ui as training data you can later turn into a better adapter.

Base URL

http://localhost:8420/v1

Model id

Qwen3.5-4B

API key

Not required — any value works

pi

Configure pi in one command: kiln pi-setup adds Kiln as pi's kiln-local provider and sets Qwen3.5-4B as the default model. It backs up existing models.json and settings.json, then merges the Kiln entries while preserving your other providers. 

kiln pi-setup
pi -p "Use the bash tool to run: pwd"

# Remote server? /v1 is appended for you:
kiln pi-setup --kiln-url http://office-kiln:8420

Backups are written beside the originals as models.json.bak-<timestamp> and settings.json.bak-<timestamp>.

opencode

Add a Kiln provider to ~/.config/opencode/opencode.json, then run opencode and pick Kiln · Qwen3.5-4B with /models. Uses the OpenAI-compatible AI SDK adapter — no API key needed. 

{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "kiln": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Kiln (local)",
      "options": {
        "baseURL": "http://localhost:8420/v1",
        "apiKey": "unused"
      },
      "models": {
        "Qwen3.5-4B": { "name": "Kiln · Qwen3.5-4B" }
      }
    }
  }
}

You should now see this request in /ui

Open http://127.0.0.1:8420/ui and watch Recent requests. The first call from pi or opencode appears within seconds, tagged with its client — proof your agent is wired in and its traffic is being captured.

Qwen3.5 can emit native XML tool calls, but Kiln returns OpenAI-shaped tool_calls to your agent in both streaming and non-streaming responses, so pi and opencode execute tools instead of printing raw XML.

4

Verify

Open the UI, check health, send chat

Open the dashboard

Visit http://127.0.0.1:8420/ui to inspect status, adapters, training jobs, and quick inference from the dashboard.

Check /health

kiln health
curl -s http://127.0.0.1:8420/health \
  | python3 -m json.tool

Send chat

curl -s http://127.0.0.1:8420/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen3.5-4B",
    "messages": [{"role": "user", "content": "What is 2+2?"}],
    "max_tokens": 128,
    "thinking_budget_tokens": 32,
    "temperature": 0.7
  }' | python3 -m json.tool

This is the first inference checkpoint: get one response before moving on to SFT or GRPO. The token budget closes an open thinking block after 32 generated tokens so the remaining completion can carry the final answer; see the API reference for the product guide and the Thinking Budget Contract for normative token, time, inheritance, and unlimited semantics.

If /ui, /health, or the chat request fails, use Troubleshooting to check the model path, binary download, CUDA/ROCm/Vulkan/Metal setup, Docker, and health checks before retrying.

Prefer terminal-first checks? See the CLI Reference for kiln health, training, and adapter commands.

5

Turn traffic into a better model

Train & evaluate

Training file shapes at a glance

kiln train sft reads SFT JSONL: one chat correction per line, each with a messages array. Rows fail closed by default; use --invalid-row-policy skip only when rejected row hashes in the final receipt are part of your review workflow. kiln train grpo reads either a GRPO JSON request/batch or JSONL with one group per line: groups of candidate completions with reward scores. kiln train opd reads one OPD request object, or a JSON prompt array with --teacher, and requires a registered exact teacher identity. See the GRPO Guide for the generate → score → train loop and the CLI Reference for full command examples.

Every route uses the same chat message schema. Assistant turns may carry OpenAI-shaped tool_calls; role: "tool" responses may carry name and tool_call_id. String, null/missing, and text-part-array content are accepted. Inline requests, local JSONL, named datasets, rollout provenance, eval, and chat-template rendering preserve these fields instead of flattening the conversation to role and text.

SFT does not append the inference generation prompt. It supervises each assistant thinking, answer, or tool-call body plus the message terminator and trailing newline; assistant role headers plus system, user, and tool-response tokens are ignored. The exact Hugging Face and TRL token/label goldens are documented in SFT Tokenization and Assistant-Only Loss.

For interruptible SFT, GRPO, or OPD, add --checkpoint-interval N; OPD defaults to 25. Job status reports the newest immutable .kiln-checkpoint basename. Continue with the identical source, route, adapter, and options plus --resume-checkpoint BASENAME; OPD also requires the exact registered teacher revision. This restores exact optimizer and loop state, not just adapter weights.

Every accepted training submission also prints and persists one exact effective seed before it enters the queue. Record that decimal string with the job ID; the dashboard keeps it visible and copyable. A resume uses the checkpoint’s original seed and rejects a mismatch. Reusing a seed is meaningful only with the same weights, data, tokenizer/template, build, backend, device/runtime, precision, kernels, and effective environment.

New checkpoints, train receipts, adapter manifests, and eval jobs also retain the loader’s complete base-weight shard manifest. Job detail shows its copyable aggregate and shard count. Exact resume rejects changed shard bytes, sizes, or multiplicity before GPU work; moving or renaming identical shards is allowed, while legacy aggregate-only checkpoints are not exact-resumable. The canonical schema is in the base-weight provenance contract.

Prove the adapter is better — evals are a peer of training

Upload an SFT or GRPO JSONL to POST /v1/eval/datasets/upload and synthesize a graded suite from it in one call — no separate eval-set authoring needed. Then POST /v1/eval/run grades any adapter, /v1/eval/compare runs the suite head-to-head against another adapter, and any training request can carry post_eval: { suite, include_baseline: true } to auto-grade itself the moment it finishes. The whole loop runs locally; the optional LLM judge is itself a LoRA you train from A/B preferences in /ui. See the Evals guide for the full walkthrough.
