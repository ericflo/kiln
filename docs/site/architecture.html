System shape

Single-process server

Kiln is built as one deployable Rust binary: a single process owns the OpenAI-compatible Axum HTTP API, request scheduler, model engine, adapter registry, and background training workers. There is no Python sidecar and no second model load for the normal SFT or GRPO path. 

client request
  -> axum HTTP/API
  -> scheduler + block manager
  -> Qwen/Qwen3.5-4B engine
  -> sampler or streaming SSE response

training request
  -> axum HTTP/API
  -> LoRA training queue
  -> hot-swapped adapter path
Prefill execution

One streaming-prefill authority for inference and training

Typed TOML and canonical startup overrides enter one strict loader. After backend selection, Kiln combines operator intent with StreamingPrefillBackendPolicy to produce an immutable StreamingPrefillRuntimeConfig. Its private execution policy is injected into ModelRunner and the server-owned training runtime. Ordinary generation, prompt-logprob scoring, SFT/GRPO/OPD admission, local teachers, MTP alignment, checkpoint planning, GDN segment forwards, tape-authoritative forwards, detached full-attention routes, and the benchmark consume that value. None of those paths rereads public streaming environment variables; server-owned teacher construction fails closed if the value is absent. 

typed [streaming_prefill] + source attribution
  -> selected-backend dispatch and tile defaults
  -> immutable StreamingPrefillRuntimeConfig
  -> ModelRunner + native training runtime + checkpoint identity
  -> inference base tiles / tape tiles / detached full-attention tiles
  -> generation / prompt-logprob + local teacher / MTP alignment
  -> inference-contract-v2 teacher and logit-cache identity

Dispatch

auto starts at 256 prompt tokens on ROCm, 2048 on CUDA/Metal, and remains off on CPU/Vulkan. enabled selects every non-empty prompt; disabled is the monolithic A/B control. A threshold override adjusts only an existing automatic crossover; eligible work physically splits only when its sequence exceeds the route tile.

Route-specific tiles

The base tile covers inference and non-tape GDN work, the tape tile covers tape-authoritative training, and the detached tile covers materialized full attention. All concrete values are positive multiples of the 64-token recurrent chunk.

Inheritance

An explicit base feeds specialized fields left on auto. A detached override feeds ordinary, boundary, and tape-replay full-attention variants. Effective-source diagnostics preserve whether a value came from backend policy, file, environment, or base inheritance.

ROCm batching also enforces route-invariant prefill chunks at startup: the actor ceiling must equal the effective 256-token streaming tile, automatic or forced streaming must cover the first split, and the combined actor budget must fit that tile plus the effective decode width. A violation stops startup before traffic instead of allowing actor and direct routes to partition a deterministic prompt differently.

The complete resolved object appears at /v1/config.streaming_prefill, health prefill_runtime.streaming_prefill, and trusted-debug top-level streaming_prefill. It has no single enabled boolean because auto dispatch is prompt-length dependent. It includes configured/backend/effective dispatch, threshold applicability, every effective tile and source, last-token LM-head policy, immutability, and restart requirement. This is process-lifetime policy; a running request or training job never observes a changed shell or file. The canonical Kiln prompt-logprob teacher identity hashes every resolved field under inference-contract v2. Changing the policy therefore changes the teacher revision and invalidates identity-bound logit caches and OPD resume bindings.

Accelerator execution

Immutable accelerator routes, attention geometry, ROCm stream ordering, and graph lifecycle

ROCm execution is process-lifetime policy, resolved once before the primary HIP context or model runner exists. Typed [accelerator] intent combines with the immutable serving profile to produce kiln.accelerator-runtime-policy.v12. The same resolved object is installed in the tensor context, projected into the model graph runner, stored in server state, and returned by product diagnostics. Tensor, model, and kernel code do not re-read the public graph, synchronization, or matmul-route environment names during inference. 

typed [server] + [accelerator] configuration
  -> strict parse, source attribution, and serving-profile gate
  -> immutable accelerator runtime policy v12
  -> Vulkan physical-device/validation policy installed before logical-device creation
  -> kiln-tensor adapter route set installed before model execution
  -> exact full-attention score geometry installed in model and ROCm flash planners
  -> primary ROCm context synchronization and matmul-route discipline
  -> ModelRunner graph lifecycle and bounded graph cache
  -> /v1/config + /health + trusted debug + dashboard + Prometheus

legacy_host_barriers

The qualified default preserves historical device and active-stream waits, including the device-wide external-yield drain and established large hipBLASLt and cast boundaries. The reasoned telemetry is new; the ordering behavior is intentionally retained.

stream_ordered

The experimental mode omits only barriers whose call site asserts a same-stream FIFO dependency. External yield waits on the primary producer stream. Host reads, borrowed-buffer lifetimes, in-place mutation, reclamation, graph transitions, recovery, and global mutation still synchronize.

One context, one policy

The primary context stores the policy. A later owner requesting another policy for the same device receives an error naming the installed and requested values; multiple model/runtime owners cannot silently mix ordering disciplines.

Adapter routes are one typed policy

accelerator.kt_api_mode replaces the former per-operation environment switches. auto enables the qualified kiln-tensor routes while leaving generic matmul and paged-KV experiments inactive; all enables the complete route set and disabled forces legacy fallbacks. The explicit comparison modes require the experimental profile. The model stores the selected value once, accepts an idempotent reinstall, and rejects a conflicting process-lifetime value rather than allowing different requests or model owners to execute different route mixtures.

Vulkan device creation is typed startup policy

accelerator.vulkan_device_index is either automatic or a strict zero-based physical-device index. Automatic selection preserves discrete-GPU preference and otherwise uses the first enumerated device; an unavailable explicit index aborts startup rather than falling back. The canonical environment name is mechanically derived as KILN_ACCELERATOR_VULKAN_DEVICE_INDEX, with KILN_VULKAN_DEVICE retained only as a warning compatibility alias. accelerator.vulkan_validation defaults false; true requires the experimental serving profile and an installed Khronos validation layer or startup fails. Both values are installed under kiln.vulkan-device-policy.v1, accept only an idempotent reinstall, and are reported in every accelerator-policy diagnostic. The nonstandard GGML_VK_VISIBLE_DEVICES behavior is removed.

Vulkan kernels use one qualified source policy

Product Vulkan dispatch uses the typed, immutable kiln.vulkan-kernel-policy.v3 object. It is not a TOML, CLI, request, or environment surface. The Vulkan backend, kernel crate, and resident model planner share this one object, so the covered model-route and packed-weight selections, recurrence residency, batch thresholds, and split-K geometry cannot diverge or change between requests. A source change must version the policy and rerun Vulkan oracle, performance, development-soak, and endurance gates. Accelerator policy v12 reports this identity as vulkan_kernel_policy_schema_id in config, health, trusted debug state, the CLI config check, and the dashboard.

Attention geometry cannot follow free-memory noise

accelerator.full_attention_score_budget_mib is a 64–2048 MiB process-lifetime ceiling, defaulting to 2048 MiB. The model planner uses it for materialized exact-attention score and scratch tiling on every backend. ROCm flash attention derives a fixed min(value, 1024) MiB online-score ceiling and retains its qualified 2048-query and 4096-key tile maxima. Memory-governor observations still protect allocations: an operation whose exact working set is unavailable is rejected before publication. They no longer choose a different tile size or route between layers or requests.

Policy v12 retains the deletion of eight permissive materialized-score, online-score, and tile environment controls rather than retaining aliases. The former planners could independently parse different values during execution and derive a materialized ceiling as high as 32 GiB from changing free memory. Real-device parity tests now force small multi-tile geometry with a scoped programmatic hook, so test coverage no longer mutates process-global configuration.

CUDA backend routes are one typed profile

accelerator.cuda_kernel_profile replaces fourteen CUDA backend hot-path environment decisions with one process-lifetime policy installed before backend construction. native_default preserves the fourteen established backend routes that were previously enabled by default; the name deliberately does not claim qualification on the current source tree or hardware. portable_fallback declines every owned accelerated route for explicit reference comparison. Reinstalling the same policy is idempotent; attempting to install a different policy after one has been observed fails instead of changing live dispatch.

The server maps the typed profile to model policy and context-owned tensor policy before device creation. Backend dispatch, model loading, forward/tape execution, Rust tensor operations, RMSNorm, and C++ paged-attention launchers all read explicit immutable values. Dispatch does not consult process environment in hot paths. A same-value process install is idempotent, a conflicting install fails, and invalid zero or inconsistent tensor geometry fails before device probing. The retired per-kernel ROCm spellings and CUDA-spelled fallbacks are deliberately unsupported as aliases, so an operator cannot create an unqualified mixture or change a route during inference. The default-off ROCm streaming-GDN and materialized tape-flash investigation switches were removed rather than promoted. The unused opt-in axis-zero concat kernel was deleted. Generic GPU MLP and split-projection environment controls remain live for CUDA/Vulkan until those hardware-host migrations, but ROCm no longer consumes them.

ROCm token-only LM head

Qualified greedy batches run the packed W8A16 tied LM head and stable argmax on-device. Sampled batches use W8A8 activation arithmetic, accept mixed greedy and stochastic rows, and apply repetition, presence, frequency, temperature, top-k, min-p, top-p, and categorical selection in the public order. Stochastic rows are bounded to top_k=1..64; unsupported settings decline to the full-logit path. Control uploads remain ordered on the active HIP stream, vocabulary scores remain device-local, and one [batch] token tensor is read back.

The seeded device draw is SplitMix64 and replays exactly only inside the same binary/device/kernel envelope; it is not a cross-backend StdRng promise. Health publishes dispatches, rows, activation arithmetic, sparse-history entries, failures, maximum batch rows, and maximum top-k at decode_runtime.rocm_w8_lm_head. Prometheus mirrors these as fixed-cardinality kiln_rocm_w8_lm_head_* counters and gauges without synchronizing the device.

Matmul route choice is fixed before inference

The primary context also owns rocm_strided_batched_matmul_mode and rocm_bf16_matmul_output_mode. Their stable auto defaults preserve the qualified gfx115x large-attention per-row fallback and the ROCm 7.2 F32-output-then-BF16-cast workaround. Explicit comparison routes require the experimental serving profile. A later owner cannot install different synchronization or matmul policy on the same device, and a GEMM cannot observe a shell mutation between layers or requests. Route decisions use only immutable policy, shape, and dtype; they do not read live memory. The obsolete matmul trace variables were deleted.

Capture and replay use a dedicated stream without weakening external visibility. A replay records completion on its capture stream, the primary stream waits on that event, and external yield then waits on the primary stream before a token becomes visible. Stable paged metadata is a correctness invariant, not a user switch. A native capture failure may trip only the graph-runner circuit breaker and continue eagerly when recoverable capture_rollback settlement and logical state restore both succeed. A replay failure, failed capture settlement/rollback, or unclassified capture exit uses fail-closed containment instead of continuing with uncertain state.

Every new multi-row graph must pass an automatic first-launch oracle before it is replayable. The eager warm pass supplies exact hidden, recurrent, convolution, and current K/V-row references. After restoring input state, Kiln launches the graph once and compares those values on device with one bounded U8 mask at a time. Snapshot, current-row gather, and mask bytes are reserved before allocation. A mismatch or comparison error settles work, restores state, discards the graph, disables graphs for that runner, and reaches eager only through the contained capture_failure path. Structured event rocm_graph_capture_parity_check reports a passed, failed, or error outcome, comparison completion, compared bytes, duration, and either mismatch attribution or the comparison error. There is no bypass setting. Health and Prometheus additionally retain monotonic batched-capture and parity attempt/outcome/byte/duration counters, so admission evidence survives log rotation and can be differenced over a benchmark window.

hipBLASLt workspace ownership follows the same lifecycle. Every fresh capture stream receives a workspace lease before its warm pass. A deferred or failed attempt settles the stream and releases its allocation; a successful graph retains the lease as its last-owned resource, so graph handles and graph-stable tensors are destroyed before the workspace is reclaimed. Retained capture workspaces therefore track the bounded live graph cache instead of accumulating across recapture history. Opaque hipBLASLt algorithm blobs are cached per device and are never shared across ROCm ordinals.

Accounting uses the allocation’s device ordinal and allocation identity, not tensor shape or Rust owner count. One physical allocation is counted once across aliases, categories, and graph entries; recurrent/conv slot state shared by several graphs for one owner is likewise deduplicated. Active graphless slot state remains in both retained_slot_state_bytes and the total because graph eviction cannot discard a live decode owner’s continuity. The four categories sum to retained_bytes, and peak_retained_bytes records the highest total after slot creation or cache admission and is never below the current total. An unmappable retained tensor makes retained_bytes_accounting_complete=false and fails byte-budget admission closed.

The cap is exact for requested physical allocation bytes, but it is not a claim about total driver residency. HIP does not expose allocation sizes for the graph, executable, private stream, or two ordering events retained by each entry. Kiln reports those five objects per graph through opaque_native_object_count; their driver overhead and allocator-pool slack remain outside retained_bytes and are covered by the separate live memory-pressure policy.

Admission, LRU eviction, and pressure are owner-aware

Entry saturation and known byte saturation first reclaim deterministic least-recently-used idle owners, oldest access tick then slot ID, before allocating a new candidate. If those cannot make room, admission orders active entries by projected owner count, then exact LRU and stable owner/geometry tie-breakers. The incoming candidate counts toward its owner's share; only the minimum selected entries are retired, one projected graph remains for every active owner, and all recurrent-state slots, row assignments, and continuity timelines remain intact. After one settled warm Record pass makes every candidate allocation measurable, pre-native admission performs exact deduplicated accounting, matching-device pressure reconciliation, an atomic process-wide governor reservation, and the same ordered reclaim plan. Native capture does not begin unless that plan fits both hard limits. Ordinary budget pressure never discards live recurrent state merely to admit a new shape. A separate overlapping governor reservation covers the automatic parity snapshots, live K/V gather, and equality mask before those temporary allocations occur; last_transient_candidate_bytes and peak_transient_candidate_bytes include that temporary working set plus the exact candidate. Each completed transaction emits rocm_graph_cache_eviction with its boundary, typed reason, removed graph and slot counts, released requested bytes, and active_graph_only_owner_count. A nonzero active count makes this settled transition visible instead of presenting its synchronization time as an unexplained inference pause.

Fairness is enforced only at actual global entry or byte saturation, so lightly occupied owners can keep reusable exact geometries without forced recapture. Idle owners remain the first victims. Narrow active relief runs at pre_capture_active_fair_share, preserves each live slot and timeline, and guarantees one retained graph per active owner after the incoming candidate. The selected owner may differ from the candidate owner when it holds a larger surplus; no unused global headroom is converted into an artificial per-owner ceiling.

The current Strix Halo mixed-load and development-soak candidate uses eight entries for eight declared active owners and pre-reserves zero transition entries. The same typed launch contract binds four ordinary decode rows, four staged-prefill slots, a 256-token/8-layer prefill quantum, and a 50 ms cooperative actor-cycle idle. Fair active relief creates transition room at actual saturation instead of holding another opaque native graph population continuously. In an earlier same-binary 120-second A/B, a 12-entry arm completed the identical first seven-wave sequence 25.3 percent faster than 24 entries while safely settling seven measured capacity transactions with zero fallback or live-slot loss; its active p50 SCLK was lower. That result motivates bounded graph residency but does not qualify eight entries or the new duty cycle. A later 32-layer mixed-load row remained thermally contained but produced fourteen nonthermal ITL outliers, so the current eight-layer quantum restores three inter-layer scheduling opportunities instead of accepting explained inference pauses. Its source-bound autoscale-off discriminator then eliminated all fourteen classified ITL outliers, reduced p99.9 ITL from 1,849.384 to 961.994 ms, and peaked at 88.75 C without a trip. Aggregate output fell from 13.885 to 12.748 tokens/second and p99 TTFT rose to 88.748 seconds, so that tradeoff remains explicit. The remaining policy arms and 30-minute soak are still required, and the profile is not a universal optimum or a reason to silently clamp an operator’s explicit configuration on another device.

Sampled fused-LM-head counters intentionally cover decode-continuation rows. Prefill owns each request’s first token, so an eight-request, 32-token qualification wave requires exactly 248 fused sample rows and independently requires all 256 response tokens through usage and semantic-oracle gates.

The first source-bound eight-layer graph-off arm outperformed its graph-on default peer for this short dynamic-shape workload: deterministic output rose from 12.935 to 13.710 tokens/second, sampled output rose from 8.319 to 14.247 tokens/second, and p99.9 ITL fell from 1,037.370 to 508.025 ms. The graph-on arm spent 3.698 seconds warming 21 candidates plus 1.532 seconds in native capture, while its maximum decode forward reached 681.762 ms versus 151.756 ms eager. That result rejects an assumption that live capture is automatically faster here; it does not replace graph correctness/resilience gates or establish a universal graph-off policy on another device or workload.

Capture and cache admission are deliberately separate outcomes. capture_successes means the native graph instantiated and its first launch succeeded. A defensive exact recheck can still reject and safely destroy that candidate if concurrent state changed before publication. cache_admission_successes is the retained, replayable subset; entry, byte, and accounting post-capture rejection counters explain the difference. Pre-capture entry/byte/accounting/global-governor skips are separate outcomes and do not explain that delta. Candidate-alone byte-budget, incomplete-accounting, and global-reservation denials are memoized by geometry and runner generation. Matching steps use the typed fallback without repeating candidate allocation and a full warm pass until observed headroom actually improves. Required active graphless slot state stays counted and may consume the whole byte allowance; the runner blocks new capture rather than dropping live continuity state merely to satisfy graph admission.

Eviction and rejected-candidate cleanup are three-stage fail-closed transactions: settle the device before ownership removal, drop graph resources and eligible slot state, then settle async frees and check cleanup quarantine again. A cached-eviction pre-drop failure leaves the cache map intact. A rejected candidate whose pre-drop settlement fails enters cleanup quarantine, so its low-level owners retain possibly in-flight handles until process exit rather than destroying them unsafely. A destructor or post-drop settlement failure records quarantined_retained_bytes, trips the same process-lifetime quarantine, reports no successful reclaimed-byte event, and forbids an eager retry. The runtime never equates “removed from a Rust map” with “safe to reuse VRAM.”

Capture pauses have fixed, live phase attribution

Exact candidate size is unknowable until the warm Record pass has allocated its stable I/O, capture arena, and private-stream workspace. That is the remaining transient exposure: the hard retained-byte limit governs publication, while the global governor gates native capture after exact measurement. last_transient_candidate_bytes and peak_transient_candidate_bytes report those deduplicated queryable candidate bytes and exclude already-owned recurrent slot state.

A cloneable telemetry handle is retained outside both the model-runner and graph-runner mutexes. It publishes current_phase and current_phase_elapsed_micros while work is still in progress, plus completed calls, slow, total_duration_micros, and max_duration_micros for exactly five non-overlapping phases: pre_candidate_headroom, candidate_warm, pre_native_reservation, native_capture, and rejected_candidate_cleanup. The first includes matching-device pressure checks and settled pre-allocation eviction. native_capture remains active through native capture, the settled first launch, defensive cache admission/publication, and the blocking committed governor debit. The last begins only when an unretained candidate enters automatic destruction and settlement. A runner lock held by a long phase therefore does not erase the phase that operators need to diagnose. A successful full rocm_graphs snapshot also carries point-in-time copies of the five completed summaries and transient-byte gauges; the separate handle is the authoritative active-phase source and continues advancing when that full snapshot is unavailable.

Governor admission validates that its probe selector matches this runner’s ROCm ordinal before reading pressure or reserving bytes. A mismatch fails closed with distinct skip/fallback telemetry. Warm-pass host-copy detection is scoped to the calling thread and device, so an unrelated concurrent copy cannot permanently classify the geometry as capture-unsafe.

Synchronization reasons are fixed telemetry dimensions

Every host-visible wait is attributed to one of 23 stable lower-snake-case reasons. The snapshot stores device wait count, stream wait count, accumulated host wait nanoseconds, and stream-ordered skip count for each reason. Reading it loads atomics only; it never inserts a barrier or calls the driver. The complete reason set is:

  • explicit_device_drain, explicit_stream_drain, tensor_handoff, external_yield
  • activation_output, elementwise_output, cast_output
  • concat_input, concat_output, contiguous_output, repeat_heads_output
  • matmul_output, matmul_cast_boundary
  • in_place_mutation, memory_reclaim, graph_boundary
  • full_attention_handoff, model_handoff, host_readback
  • allocation_lifetime, error_recovery, global_state_mutation, capture_rollback

error_recovery is reserved for a device whose process-lifetime execution quarantine was already published; it waits for pre-quarantine host submissions to settle before the diagnostic drain. capture_rollback is the distinct recoverable path: it drains a failed capture before a proven logical rollback while leaving execution admission open. Calling the fatal recovery path on an open gate is rejected rather than silently changing either contract.

Successful physical settlement plus successful recurrent-state restoration disarms the capture guard; the runner may disable further graph work, record capture_failure, and take the eager path. Failed settlement, failed logical restoration, or an armed/unclassified guard leaving scope publishes sticky STOP before the post-STOP diagnostic drain attributed to error_recovery. That drain is diagnostic only: even if it succeeds, execution stays cleanup-quarantined and the process must restart.

Wait duration belongs to the boundary where the host discovered outstanding work. It is not a per-kernel profiler and does not prove which earlier operation consumed the time. For example, a large external_yield delta can expose work accumulated earlier on the producer stream. A VRAM-rebalance claim additionally needs allocator reclaim, physical KV resize, memory-tier, or host-pressure evidence. A new graph bucket can instead produce a one-time warmup/capture pause.

Source-bound ROCm and Vulkan development soaks add an independent qualification-only device sampler; it is not a second product configuration surface. Every 250 ms the harness resolves exactly one AMD 0x1002 DRM device and one labeled amdgpu hwmon, then records GPU busy, sclk, PPT average power, and edge temperature. Active aggregates include only samples at or above 50 percent busy and publish minimum/p50/maximum SCLK, p50/peak power, p50/peak temperature, and a count below half the advertised pp_dpm_sclk maximum. ROCm receipts fail closed on unavailable, malformed, empty, or idle-only telemetry. Vulkan records the same closed metric schema when AMD sysfs exists but may report it unavailable on a non-AMD Vulkan device. This evidence can distinguish a device-wide clock or thermal state from graph, allocator, and synchronization events; correlation still does not make any one sample a kernel-level causal profile.

Native ROCm graph capture owns single-row decode and contiguous BF16 multi-row decode. Batch graphs are keyed by width plus bucketed attention geometry and retain stable token, position, RoPE, paged-KV metadata, attention scratch, hidden-output, and recurrent-state storage. The historical multi_row_batch_unsupported reason stays in the closed schema, but a supported current batch route must leave it at zero and publish real capture/replay activity.

Graph-slot liveness is live row ownership, not retained cache residency. A slot with an assigned logical row is active. A reusable single-row slot or a slot reserved for a batched width is idle between cohorts, even while its native graphs, recurrent state, and width mapping remain resident and byte-accounted. A drained boundary therefore requires zero active slots and zero tracked decode owners; positive idle slots are bounded reusable capacity rather than leaked requests.

Capture success is published only after rocm_graph_capture_parity_check passes exact hidden, complete GDN state, and current-row K/V comparison with the same candidate’s eager warm execution. A failed check is a capture failure, not an admitted graph whose later output happens to be inspected. In the cumulative counters, batched attempts and parity checks each reconcile to their closed outcomes, and successful batch admissions cannot exceed passed checks. A clean qualification row additionally requires zero failures/errors and equal success/pass counts; a pass followed by a later admission failure remains visible as failure evidence.

Capture-safety host transfers are separately source-attributed as event=rocm_graph_capture_host_transfer. The dynamic observer is local to the capture thread and device, aggregates copy count and bytes by build-source file/line/column, dtype, and per-copy geometry, and bounds each candidate to 32 unique sites plus one overflow aggregate. These fields stay in structured logs; they are deliberately excluded from Prometheus labels and contain no request or tensor contents.

Materialized ROCm broadcast keeps graph ownership self-contained. Its rank-eight shape and stride descriptor is a 272-byte kernel value captured in the graph node, not a device buffer populated by four host uploads. Replays therefore do not depend on an evictable metadata cache or an allocation whose lifetime is outside the retained graph entry.

A fatal execution or synchronization failure marks the device cleanup-quarantined for the rest of the process lifetime. The flag is shared across every context for that device ordinal; a later recovery drain may collect evidence but cannot re-enable execution or cleanup. New execution fails closed and Drop retains possibly in-flight streams, events, allocations, graphs, and graph executables until process exit rather than risking use-after-free. Graph code must not fall back to eager execution after a failed recovery. Active ROCm telemetry unavailability is also fail-closed rather than interpreted as a false bit. The central server admission gate observes and permanently latches either condition before adapter, training, import, or other backend mutation work. The live fault makes backend runtime health fail closed and readiness return 503. It appears in health and trusted debug, while kiln_rocm_cleanup_quarantined provides alerting; its value is authoritative only when the telemetry-availability gauge is one. This state is deliberately absent from /v1/config, which describes immutable startup intent.

The stable product default is legacy_host_barriers with graph mode profile, which resolves to eager disabled execution. Stream-ordered and explicit non-disabled graph modes fail startup outside the experimental profile. Promotion requires local hardware evidence for token/logit parity, concurrency throughput, p50/p95/p99/max inter-token latency, reasoned wait time, graph fallbacks, memory peaks and plateaus, cancellation, and sustained stability. The reversible procedure is in ROCm token-pause troubleshooting; the field and environment migration contract is in the complete configuration reference.

Inference flow

Request path and batching

API edge

/v1/chat/completions, /v1/models, /health, and streaming responses stay compatible with familiar OpenAI-style clients.

Scheduler

The iteration-level scheduler combines continuous batching with chunked prefill, so long prompts and decode work share one GPU loop.

Memory

The paged KV block manager tracks the full-attention layers and reuses recently released runs before untouched sparse pages. Qwen3.5-4B’s Gated DeltaNet layers do not need KV cache.

The locality policy preserves a released request’s logical block order while moving that run to the front of the allocator. This avoids walking an entire host-resident Vulkan KV pool and first-touching new anonymous or transparent-huge pages during otherwise steady traffic. Prefix-cache leases still retain their blocks, and logical shrink still retires capacity before any physical pool replacement. Vulkan’s bounded scratch recycler separately uses exact buckets for device-local buffers; host-visible staging checks its exact bucket first and then the smallest sufficient idle larger bucket on the same device and memory type. A borrowed, undersized, or cross-device buffer is never reused.

Prefix-cache route invariance

On the batching actor, cache admission changes storage and reuse, not numerical prefill geometry. A cache-enabled miss and a cache-disabled fresh prefill keep the same block-aligned final prompt boundary and the same configured token and layer quanta. With caching disabled, Kiln performs no lookup, recurrent-state snapshot, prompt registration, rolling snapshot, retained-block publication, or lease.

The distinction is correctness-critical for hybrid GDN models. Every resumable prompt-chunk boundary materializes recurrent state at the configured precision; changing the boundary can change greedy output even when the cache has never served a hit. Route-equivalence coverage therefore compares the first token, recurrent state, and following decode token with registration enabled and disabled. Accelerator qualification remains required before a corrected source checkpoint can replace a failed device receipt. On Strix Halo ROCm, the clean-source production replacement arm passed all ten deterministic and eight sampled requests while every cache metric stayed zero; the historical failed receipt remains published so the correction is auditable rather than overwritten.

Conservative terminal drain

Batching health keeps a terminal row publicly active until normal finish or error/cancellation discard has released its graph owner, recurrent-state lease, prefix-cache ownership, and private KV blocks. The row has already left the private scheduling vector and cannot run again, but its removal is not published until model cleanup returns and terminal delivery is queued. A zero-active health snapshot is therefore a resource-ownership boundary, not merely an empty scheduling queue; graph, cache, and block drain assertions cannot race terminal cleanup.

Vulkan cross-request prefix reuse

Production currently correctness-quarantines the complete Vulkan prefix cache. A guarded fresh-process run with resident token-prefill already disabled produced four correct first-wave responses, then four semantically wrong exact repeats after restoring cached KV and GDN state. The repeated prompts therefore use fresh generic prefill instead of accepting internally plausible but incorrect restored state.

prefix_cache.enabled remains typed operator intent and defaults to true. Startup combines it with the selected backend. CPU, CUDA, ROCm, and Metal currently honor the request; Vulkan forces the effective capability false, allocates zero cached blocks and recurrent-state bytes, and does not perform lookups or registrations. GET /v1/config reports both the configured object and effective_reason="vulkan_correctness_quarantine". Health, trusted debug state, and kiln_batching_engine_prefix_cache_enabled 0 expose the live result.

While disabled, every lookup, hit, miss, retained-block, retained-entry, state-byte, lease, and pending-release value must stay zero. Qualification checks that invariant after warmup, every stabilized and measured wave, and final drain. There is no request or environment bypass. Re-enablement requires a source change plus production-model semantic parity across first use, exact repeats, strict descendants, changing cohorts, cancellation, and repeated process history.

Vulkan resident token-prefill

Production currently disables this optimization and publishes resident_prefill_enabled=false. Guarded Qwen3.5 Vulkan runs produced plausible but semantically incorrect token sequences, including on the first resident-prefill use in a fresh process. Every prompt therefore stays on the generic layer-resumable prefill path. This is a correctness quarantine, not an operator setting, and there is no environment variable or request override that can bypass it.

The dormant route remains lifecycle-tested so it can be repaired without losing its ownership model. Its intended eligibility is effectively greedy, adapter-free work at a committed token boundary with no behavior-logprob capture or partial layer chunk. It would advance one token per row through a bounded round-robin cohort, retain stable row IDs as cohort shape changes, and keep a final resident row on that route rather than returning to stale generic KV. None of those transitions are admitted while the capability is false.

Health and trusted debug state must report the capability as false, and every resident-prefill activity counter, batch-size gauge, active-row gauge, and request-level resident_prefill_used value must remain zero or false. Prometheus exposes the same capability as kiln_batching_engine_resident_prefill_enabled 0. Qualification treats any resident-prefill activity while disabled as a contract failure. Re-enabling requires a source change plus production-model parity across first use, changing cohorts, single-row tails, repeated waves, cancellation, and prefix history; scheduler lifecycle tests alone are not sufficient.

Model architecture

Why the Gated DeltaNet hybrid matters

Qwen3.5-4B is not a plain all-attention transformer. Its 32 layers are split into 24 Gated DeltaNet linear-attention layers and 8 full GQA layers, and Kiln is tuned around that exact shape instead of hiding it behind a generic model-family abstraction.

Fixed GDN state

Gated DeltaNet layers carry fixed-size recurrent state through the sequence instead of storing per-token K/V tensors.

Small KV footprint

Only the 8 full-attention GQA layers need KV cache, which is why long context can fit on one GPU.

Targeted kernels

GDN handles most layers with recurrent linear attention while GQA handles periodic full-attention checkpoints.

For the detailed recurrence, paging, and kernel discussion, read the full ARCHITECTURE.md deep dive.

Live learning

LoRA hot-swap and training queue

Training requests enter the same server through /v1/train/sft or /v1/train/grpo. A FIFO background queue trains LoRA adapter weights against the loaded base model, checkpoints progress, then publishes the new adapter atomically at an iteration boundary. Subsequent inference requests see the updated adapter without restarting the server.

SFT

Correct input/output examples update adapter weights directly from supervised loss.

GRPO

Scored completions become a generate → score → train loop through the same HTTP API.

Inspect your live server’s queue and registry: kiln train status shows pending and running jobs, and kiln adapters list shows the published adapters available to subsequent requests. 

kiln train status
kiln adapters list

SFT loss authority

Backend-owned SFT loss routing

The selected training backend owns one typed SftFlceLossRoute capability. It is deliberately absent from the SFT request, SftConfig, and typed [training] configuration, so there is no TOML field and no mechanically derived environment name. The former KILN_USE_FLCE switch is removed: it has no compatibility alias and no current routing effect.

This capability matrix defines routing and admission behavior; it is not hardware qualification evidence. Route-specific saturating admission accounts for the loss workspace. A rejected memory estimate reports loss workspace ... (route=<route>) in the HTTP 413 detail. full_logits materializes dense [T,V] logits, so a multi-segment checkpoint plan fails before queue publication with training_invalid_request instead of silently selecting a different loss path. 

resident TrainingLossBackend capability
  -> route-specific saturating preflight + checkpoint compatibility guard
  -> PreparedSftAdmission pins SftFlceLossRoute
  -> queue recheck before governor reservation / KV replacement / allocator reclamation
  -> pinned TrainingRuntimeContext
  -> fresh execution-backend comparison before resident or trainable allocation
  -> every standard or checkpointed SFT step uses the admitted route

Completed SFT receipts expose the decision as runtime.sft_loss_route. Exact SFT checkpoints bind it under kiln.training-checkpoint-planning.v4; prior SFT v3 identities fail closed as planning drift, while GRPO and OPD remain on kiln.training-checkpoint-planning.v3. The generated Native SFT Profile is the complete normative contract.

GPU path

GPU backend crates

Kiln keeps the Qwen3.5-4B fast path in Rust crates with focused native kernels where the model needs them. CUDA builds use vendored FlashAttention-style kernels and paged GQA decode paths, Vulkan builds use ash plus embedded SPIR-V shaders for AMD/Intel Linux GDN hot paths, and Metal builds use candle-metal plus Kiln's Apple Silicon shader family. The result is a small codebase tuned for one model instead of abstracting over many model families.

  • kiln-server owns HTTP routing, configuration, metrics, and API surfaces.
  • kiln-scheduler and kiln-core coordinate batching, requests, and KV blocks.
  • kiln-model loads Qwen3.5-4B weights, applies adapters, and drives the forward pass.
  • kiln-flash-attn, CUDA-backed crates, kiln-vulkan-kernel, and Metal shaders provide backend-specific GPU kernels.
  • kiln-train defines the SFT, GRPO, and identity-bound OPD training APIs, exact checkpoint state, and job lifecycle.
  • kiln-eval defines eval suites, scorers, results, and dataset → suite synthesis (pure CPU).
Eval pipeline

Evals as a peer of training

The eval pipeline mirrors the training queue but rides the inference read-lock so it can run concurrently with both serving and training. A second FIFO worker pulls QueuedEvalJob entries from state.eval_queue, resolves the requested suite from SuiteRegistry (or uses an inline copy), drives the in-process generator across every example, and writes per-example outcomes plus a headline accuracy into EvalJobInfo. A streamed progress callback updates a running_accuracy field after every example so the /ui drill-in modal renders live.

Suite registry

Suites are versioned JSON under <eval-root>/suites/. POST /v1/eval/suites registers; POST /v1/eval/run grades any adapter against them.

Dataset → suite

Upload an SFT or GRPO JSONL to persist content-addressed, group-aware train/validation/holdout views. Training defaults to train; synthesis defaults to holdout before applying final_assistant, every_assistant_turn, or tool_call_predict.

Post-training auto-eval

SFT and GRPO may carry a held-out post_eval. Admission rejects exact, normalized, row, group, or session overlap before training; explicit train-set-eval runs are diagnostic-only.

Judgment flywheel

A/B/Tie/Skip preferences from /ui append to a JudgmentStore, compile to an SFT dataset, train a local judge LoRA, and that judge grades future suites — no frontier LLM called.

Full pipeline diagram and request shapes live in the Evals guide and ARCHITECTURE.md › Evaluation Pipeline.
