Troubleshooting · first-run checks

If Kiln does not start cleanly, check these first.

This page is a compact diagnosis guide for cold-reader setup issues. It does not replace the Quickstart; use it when a command fails, /health is not green, or the server is running but not using the model or adapter you expected.

Start with three probes

Binary

Pick the release artifact for your OS and accelerator: Linux/Windows CUDA builds for NVIDIA GPUs, the Linux Vulkan build for AMD/Intel GPUs, or the Apple Silicon Metal build on macOS arm64.

Model path

Point Kiln at the local Qwen3.5-4B weights with KILN_MODEL_PATH or --model-path. The path must contain the downloaded safetensors and tokenizer files.

Health

After startup, ask /health what the server actually loaded before trying chat, SFT, GRPO, or adapter calls.

If the kiln CLI is on your PATH, run kiln health for the same info as a readable tree (use --json for scripts and --url http://host:8420 for remote servers). The curl commands below are the equivalent HTTP probes — handy for CI, scripts, or any environment without the CLI. 

curl -s http://localhost:8420/health | jq .
curl -s http://localhost:8420/v1/models | jq .
curl -s http://localhost:8420/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"Qwen3.5-4B","messages":[{"role":"user","content":"Say hi."}],"max_tokens":16}' | jq .
Desktop App first launch

If the Desktop App does not finish first launch

The Desktop App wraps the same Kiln server, model path, GPU driver, and local port checks. If setup stalls, open the app's Logs view first, then compare the message with these common recovery paths.

  • If the server binary failed to download or verify, retry the download and confirm the app can write to its data directory.
  • If the model path is unset or missing weights, choose the local Qwen3.5-4B directory that contains safetensors, config, and tokenizer files.
  • If the CUDA driver is too old or an update is blocked on Linux or Windows, update the NVIDIA driver before launching the CUDA server.
  • If a Vulkan build falls back to CPU, run vulkaninfo --summary and confirm the AMD/Intel GPU is listed before launching the Vulkan server.
  • If the port is already in use, stop the other Kiln/server process or change the Desktop App server port before restarting.
  • If Settings shows a load or recovery warning, review the preserved values and defaults before saving the repair. Automatic server launch stays off while the warning is unresolved; a newer settings schema requires a Desktop App update.
  • If the server enters a crash/restart loop, open Logs, fix the first setup error shown there, then restart from the app.
  • For app-specific paths and log locations, see the Desktop troubleshooting notes.

Wrong binary or GPU path

Symptom

The binary exits early, reports no usable accelerator, or starts with much lower performance than expected.

Check
  • Linux and Windows CUDA builds require an NVIDIA GPU.
  • Linux Vulkan builds require a Vulkan 1.2+ AMD/Intel driver; vulkaninfo --summary should list the target GPU.
  • CUDA release builds target CUDA 12.4-era systems.
  • macOS uses the Apple Silicon Metal artifact, not a CUDA or Vulkan artifact.
Fix

Download the matching artifact from GitHub releases. Select Vulkan through typed accelerator.vulkan_device_index; auto preserves discrete-GPU preference and an explicit unavailable index fails immediately. The memory-probe identity gate currently permits startup only when the selected index is zero and exactly one relevant physical DRM device exists. An available nonzero or multi-device selection therefore fails before model upload instead of measuring another GPU. KILN_VULKAN_DEVICE is only a deprecated typed-config alias, GGML_VK_VISIBLE_DEVICES is unsupported, and driver remaps such as MESA_VK_DEVICE_SELECT or DRI_PRIME are rejected. CUDA/ROCm visibility variables remain subject to the same interim identity guard, so use a bare-host single-GPU launch or CPU until PCI-address/UUID-bound probing is available.

Memory admission fails or Vulkan pauses under pressure

Symptom

Startup refuses a KV allocation, memory headroom unexpectedly becomes zero, or a Vulkan process previously paused or destabilized the host while allocating its cache.

Check
  • Inspect /v1/config at vram.live, including sample age, staleness, sampler health, and raw_observations.host_backed.
  • For Vulkan, inspect vram.vulkan_buffer_pool and /health at vulkan_buffer_pool. Growing retained bytes indicate recycler working-set growth; flat retention with growing RSS indicates a different ownership or page-residency mechanism. Route-specific misses identify device-local versus host-visible growth; host-visible lookup may legitimately hit a larger compatible idle bucket.
  • On Linux Vulkan, compare primary VRAM with the host-backed GTT tier. A 96 GiB firmware VRAM carveout does not mean Linux can safely allocate a 96 GiB host-resident KV cache.
  • If live ownership is flat but anonymous RSS grows, inspect AnonHugePages in /proc/<pid>/smaps. Repeated fixed-shape requests should reuse recently released KV blocks instead of continuously first-touching untouched pool pages.
  • Check host MemAvailable and every applicable cgroup memory.max/memory.high ancestor.
Fix

Reduce memory.num_blocks or memory.inference_memory_fraction in kiln.toml, reduce prefix_cache.max_entries, lower memory.vulkan_buffer_pool_gb, or disable the prefix cache. A zero Vulkan pool cap disables scratch retention; active operations may still need temporary memory. Free host memory or raise the deliberate cgroup limit. Do not bypass a missing, stale, or unhealthy sample: Kiln treats it as zero headroom so a zero-filled allocation cannot take down the process or host.

curl -s http://localhost:8420/v1/config | jq '.vram.live'
curl -s http://localhost:8420/health | jq '.gpu_memory.live, .vulkan_buffer_pool, .decode_runtime.memory_governor'
curl -s http://localhost:8420/metrics | grep -E 'kiln_gpu_memory_(probe_failed|sample_|sampler_)|kiln_gpu_host_backed_memory_bytes|kiln_vulkan_buffer_pool'

Inference pauses or throughput collapses at concurrency

Symptom

Streaming appears to pause between tokens, time to first token grows with queued prompts, or a wide CUDA/ROCm/Vulkan run stops scaling even though requests eventually complete.

Check
  • Inspect GET /v1/config at batching: require an active actor, effective mode enabled, and rowwise_decode.enabled=false for ordinary throughput.
  • Inspect batching.direct_decode_rendezvous separately. worker_active=true does not mean traffic uses it; route_available is false whenever the actor is active.
  • Compare the configured, backend-policy, effective, and source values for decode width and prefill_admission_quantum. Deterministic mode or token budget can clamp both.
  • Request include_performance=true and compare actor_queue_ms, actor_admission_ms, and actor_prefill_wall_ms with live actor, allocator, reclaim, and KV-resize metrics.
Fix

Put the eight controls in [batching], restart, capture the resolved object, and change one field per A/B. Restore rowwise_decode=false for throughput. A smaller admission quantum can isolate prompt-admission delay but may reduce batch fill; actor-disabled mode is an isolation comparison, not a performance fix. Do not tune direct-rendezvous fields for an actor-backed run.

curl -s http://localhost:8420/v1/config \
  | jq '.batching, .decode_runtime.max_decode_batch'
curl -s http://localhost:8420/health \
  | jq '.decode_runtime.batching_configuration, .decode_runtime.batching_engine, .decode_runtime.direct_decode_rendezvous, .decode_runtime.memory_governor'
curl -s http://localhost:8420/metrics \
  | grep -E 'kiln_batching_engine_|kiln_gpu_memory_|kiln_kv_'

Do not label a scheduling pause as VRAM rebalancing without a matching reclaim, physical resize, synchronization, or memory-pressure event. A long actor queue/admission/prefill phase and a device-memory operation are different hypotheses and require different evidence. CUDA/Vulkan automatically admit up to effective decode width; ROCm/Metal/CPU default to 4, clamped to that width. Every batching change is process-lifetime policy and requires restart.

The direct rendezvous scope is exactly actor-absent direct streaming effectively-greedy requests. Sampled and non-streaming requests bypass it. If intentionally diagnosing that fallback, disable the actor, restart, and require route_available=true; then change one of its mode, maximum-batch, wait-microsecond, or mixed-sequence fields at a time. Automatic tuples are CPU (8,0,false), CUDA (1,0,false), ROCm (8,0,false), Metal (8,100,true), and Vulkan (64,5000,true), with width clamped to effective decode width. Malformed canonical or deprecated values fail startup instead of silently selecting a fallback.

CUDA backend-profile diagnosis

Inspect accelerator_runtime.cuda_kernel_profile before attributing a CUDA route change. native_default preserves the fourteen established backend routes but is not itself a qualification claim; portable_fallback declines all fourteen. The policy is immutable after startup and its source identifies TOML, canonical environment override, or default ownership. 

curl -s http://localhost:8420/v1/config \
  | jq '.accelerator_runtime | {schema_id, version, cuda_kernel_profile}'
  • Use accelerator.cuda_kernel_profile = "portable_fallback" only as a whole-profile comparison, restart, and preserve both resolved config objects with the same model, request, seed, batch, and memory policy.
  • Do not use former CUDA-specific per-kernel environment switches. They are not aliases and cannot establish which route ran.
  • A difference between profiles localizes the problem to one of the fourteen documented backend routes; it does not identify a particular route. Use route counters, profiler evidence, and a focused reproduction before drawing that conclusion.
  • Controls outside the fourteen backend-owned routes remain separate migration work. The profile must not be interpreted as a complete CUDA qualification or as authority over graph, forward, training, or Marlin controls not listed in the architecture table.

Vulkan kernel-policy diagnosis

The production selections documented for kiln.vulkan-kernel-policy.v3 are fixed. Their former KILN_DISABLE_VULKAN_*, KILN_ENABLE_VULKAN_*, kernel-threshold, split-K, stage-profile, packed-weight, recurrence, and resident-decode variables are not controls and must not be used to explain a run. The backend, kernel, and resident-model planners share one source object for those decisions; malformed shell values cannot select a fallback. 

curl -s http://localhost:8420/v1/config \
  | jq '.accelerator_runtime | {schema_id, version, vulkan_kernel_policy_schema_id, vulkan_device_policy_schema_id, vulkan_device_index, vulkan_validation}'
  • Remove old kernel switches from launch scripts. They have no compatibility aliases or replacement fields.
  • Compare the binary/source commit and policy schema before comparing receipts. A route change requires a reviewed source revision and renewed Vulkan parity, performance, and soak evidence.
  • Use typed batching, memory, prewarm, and accelerator fields for supported operator decisions. Do not infer a hidden model-route or kernel override from a throughput change.
  • Historical optimization logs and the Vulkan microbenchmark document research experiments; neither defines the product runtime contract.
  • Select a device with typed accelerator.vulkan_device_index = "auto" or a strict zero-based index. Invalid explicit indices fail startup; they never fall through to another GPU.
  • Enable validation only with typed accelerator.vulkan_validation = true under the experimental profile. Startup fails when the Khronos validation layer is unavailable, so diagnostics cannot claim validation that was not active.
  • The serving/kernel product no longer reads residual KILN_VK_* tiling or CPU-fallback controls. The separate research executable uses only typed CLI arguments and cannot define a qualified product receipt.

The current clean-source Strix Halo Vulkan development soak passed safety and lifecycle gates but remains plainly uncompetitive: 55 requests and 880 output tokens over 1,935.219 measured seconds produced only 0.455 aggregate output tokens/second, with 83.194-second p50 and 150.588-second p99 TTFT. All 228 ITL outliers were attributed and none were unexplained. Process DRM and live/retained Vulkan ownership ended byte-identical to baseline; measured allocation, free, pool-miss, eviction, and uncached-allocation counts were zero, RSS grew 1.17 MiB, and swap did not grow. The 89.75 C package peak did not trip the 97 C guard, and shutdown was clean. That evidence contradicts a mid-inference VRAM-rebalance explanation for these long phases; it does not make the latency or throughput acceptable, establish vLLM parity, or replace the final eight-hour common-source endurance run.

Vulkan prefix-cache diagnosis

Vulkan currently correctness-quarantines all cross-request prompt, KV, and recurrent-state reuse. A conforming process reports the configured intent separately from an effective false capability and fresh-prefills exact repeats. Do not interpret zero hits as a tuning or capacity problem on this backend. 

curl -s http://localhost:8420/v1/config | jq '.prefix_cache'
curl -s http://localhost:8420/health | jq '.prefix_cache, .decode_runtime.batching_engine.prefix_cache_enabled'
curl -s http://localhost:8420/metrics | grep '^kiln_.*prefix_cache'
  • Require effective_enabled=false, effective_reason="vulkan_correctness_quarantine", health prefix_cache.enabled=false, and actor prefix_cache_enabled=false.
  • Every lookup, hit, miss, hit-token, hit-block, cached-block, maximum-block, cached-entry, maximum-entry, state-byte, lease, and pending-release value must be zero.
  • Changing prefix_cache.max_blocks or max_entries cannot enable the cache on Vulkan. No request field or environment alias bypasses the source-level gate.
  • A nonzero activity value, an exact repeat that takes a cache route, or an effective true capability means artifact drift and requires stopping the process before trusting output.
  • Re-enablement requires production-model oracle parity across first use, exact repeats, strict descendants, changing concurrency, cancellation, and repeated history.

Vulkan resident-prefill diagnosis

Production currently correctness-quarantines the native token-prefill optimization after guarded Vulkan runs returned semantically wrong tokens. Start every incident check by requiring resident_prefill_enabled=false. Every attempt, forward, decline, route-failure, row, completion, and batch-size field must remain zero; active_resident_prefill must also remain zero. Any activity means the running artifact does not implement the current production contract. 

curl -s http://localhost:8420/health \
  | jq '.decode_runtime.batching_engine | with_entries(select(.key | contains("resident_prefill")))'
curl -s http://localhost:8420/metrics \
  | grep '^kiln_batching_engine_.*resident_prefill'
  • The generic layer-resumable prefill route remains authoritative. There is no supported environment variable, config field, or request override that enables resident token-prefill.
  • kiln_batching_engine_resident_prefill_enabled 0 is the Prometheus equivalent of the health capability.
  • A request-level resident_prefill_used=true is impossible in a conforming production process and should be treated as artifact or contract drift.
  • Re-enablement requires production-model semantic parity across changing cohorts and repeated process history. Scheduler counters or a successful HTTP response are not sufficient evidence.

CUDA graph capture is absent, unstable, or unexpectedly eager

Establish policy

Inspect the typed request before attributing behavior to capture. The default stable serving profile disables live graph capture even when memory.cuda_graphs=true.

Check the bound

memory.cuda_graph_cache_entries is 1..=64, defaults to 8, and is fixed before device selection. Changing it requires restart; malformed, zero, and oversized values stop startup.

Do not bypass invariants

Stable paged metadata is mandatory and batched capture is unavailable. Former stable-metadata, batched-enable, no-replay, force-eager, and batched-KV environment probes are retired; setting them cannot alter CUDA decode.

curl -s http://localhost:8420/v1/config | jq '.cuda_graphs'
curl -s http://localhost:8420/health | jq '.decode_runtime.cuda_graphs'
kiln config --file kiln.toml

Use server.serving_profile="experimental" only for controlled qualification. A CUDA feature compile on a non-NVIDIA host is not runtime evidence. Re-enabling batched capture requires a source change plus real NVIDIA sanitizer, eager-parity, resilience, and throughput evidence; it cannot be promoted through configuration.

ROCm token pauses or irregular decode latency

Symptom

Token delivery stops briefly during an otherwise healthy ROCm decode, inter-token latency has a long tail, or a new decode shape pauses once and then runs normally. A pause alone is not evidence that Kiln rebalanced VRAM.

Attribute before tuning
  • Capture GET /v1/config at top-level accelerator_runtime, rocm_graphs, rocm_graphs_unavailable_reason, rocm_graph_telemetry, and rocm_graph_telemetry_unavailable_reason so immutable policy, full cache state, and the independent phase channel are all part of the result. A null value means unavailable data, not zero activity.
  • Compare health decode_runtime.rocm_synchronization before and after the request. Rising wait time in external_yield, eager-output, matmul, or handoff reasons supports a synchronization-boundary hypothesis.
  • Inspect decode_runtime.rocm_graphs. Check full state/unavailable_reason separately from phase_telemetry_available/phase_telemetry_unavailable_reason. A live current_phase, phase latency growth, transient candidate bytes, new capture attempts, deferrals, admissions, pre/post admission decisions, evictions, retained-byte changes, or fallback duration around a new shape support a graph-lifecycle hypothesis.
  • Require matching allocator reclaim, physical KV resize, primary/host-backed memory movement, or host pressure before calling the event VRAM rebalancing.
Interpret carefully

waited_ns measures host wall time at the named boundary. It identifies where the host observed unfinished GPU work, not necessarily which earlier kernel produced it. Correlate reason deltas with actor phase timing, graph counters, memory telemetry, and token timestamps rather than treating one counter as a causal profile.

Record the immutable policy and reasoned telemetry

Trusted debug must already be enabled; do not expose it merely to collect this comparison. The synchronization snapshot is a fixed 23-reason atomic read and does not wait on the device or probe the driver. Prometheus separates device and stream wait counts by {reason,scope}, host wait seconds by {reason}, and barriers deliberately skipped by stream-ordered policy. telemetry_available=false invalidates the synchronization comparison instead of implying zero waits. Require cleanup_quarantined=false and kiln_rocm_cleanup_quarantined 0 while telemetry is available. A quarantine is a hard safety fault, not a normal capture fallback: stop the arm, preserve the health/metrics/log evidence, and restart the process before resuming service. Quarantine is process-lifetime sticky; a later recovery drain cannot clear it. Active ROCm telemetry loss is equally fatal, even when the quarantine bit reads false. The shared backend gate rejects inference, adapter, training, and import admission once either condition is observed. The runtime rejects new execution and retains possibly in-flight HIP resources until process exit rather than destroying them without proof of quiescence.

Full graph-cache observation does not wait for the runner locks. Require kiln_rocm_graph_telemetry_available 1 before interpreting cache, counter, or fallback families. A zero availability value explains why those families are absent from that scrape; it does not mean the cache is empty. Read the one-hot kiln_rocm_graph_snapshot_unavailable{reason} family rather than guessing. The same condition appears as null rocm_graphs plus rocm_graphs_unavailable_reason in config and trusted debug. Health reports state="busy" only for model_runner_busy or graph_runner_busy; it reports state="unavailable" for backend_without_graph_runner, model_runner_lock_poisoned, or graph_runner_lock_poisoned. Do not ascribe every null to lock contention. The independent phase handle lives outside both runner locks, so it remains readable for every real backend through model-runner or graph-runner contention and poison. Require kiln_rocm_graph_phase_telemetry_available 1, then use kiln_rocm_graph_current_phase, its elapsed-seconds gauge, and fixed phase duration families to identify a headroom, warm, reservation, native-capture/publication, or cleanup pause while it is occurring. native_capture includes the settled first launch, defensive cache admission/publication, and blocking committed governor debit; rejected_candidate_cleanup begins only when an unretained candidate enters destruction and settlement. When phase availability is zero, inspect kiln_rocm_graph_phase_telemetry_unavailable{reason}; currently only backend_without_graph_runner can be active there, though the family uses the same closed five-reason schema. The two availability gauges govern only their own metric families.

Run a controlled legacy versus stream-ordered A/B

Use the same binary, model, request corpus, prompt order, seed, sampling parameters, memory budget, batching configuration, concurrency, and warmup. Run the arms serially after separate restarts. Both arms use the experimental serving profile because stream_ordered is qualification-only; both explicitly disable graphs so capture does not become a second changed variable. 

# rocm-legacy.toml
[server]
serving_profile = "experimental"

[accelerator]
rocm_synchronization_mode = "legacy_host_barriers"
rocm_graph_mode = "disabled"
rocm_graph_cache_entries = 8
rocm_graph_cache_max_bytes = 1073741824

# rocm-stream-ordered.toml: identical except this field
# rocm_synchronization_mode = "stream_ordered"

kiln config --file rocm-legacy.toml --backend rocm
kiln serve --config rocm-legacy.toml
# Stop the first server before starting the second arm.
kiln config --file rocm-stream-ordered.toml --backend rocm
kiln serve --config rocm-stream-ordered.toml

Save pre/post health and metrics snapshots for each arm. Compare token or logit parity, completed requests, throughput at concurrency 1/8/16/32/64, p50/p95/p99/max inter-token latency, per-reason wait and skip deltas, and primary plus host-backed memory peaks and post-run plateaus. Stop the arm on a parity error, replay/capture failure, cleanup quarantine, OOM, telemetry loss, host-memory pressure, or incomplete request. A lower wait count without parity and stability is not a pass.

legacy_host_barriers remains the qualified default. It preserves historical device and active-stream waits, including a device-wide external-yield drain. stream_ordered skips only call sites proven FIFO-ordered on the same HIP stream and changes external yield to a primary stream wait. Host readback, buffer lifetime, in-place mutation, allocator reclaim, graph transition, error recovery, and global-state drains still wait.

Compare disabled with warmup_then_eager before testing native capture. A one-time pause paired with new capture counters can be a deterministic bucket transition; repeated fallback growth or replay failures are not. Graph replay records completion on its capture stream, orders that event into the primary stream, and only then permits the external-yield wait to publish progress. Isolate prefix-cache state separately

If deterministic output still differs after graphs and KV autoscaling are disabled, compare the committed both-off arm directly with both-off-prefix-cache-off. The latter writes prefix_cache.enabled = false in the generated typed launch file; do not inject an environment override. It must report a false batching capability and zero cache capacity, lookup, hit, lease, pending-release, retained-block, entry, and recurrent-state-byte evidence at every attested boundary. Its receipt retains the enabled bit, baseline residency, lookup/hit deltas, and final residency. Do not interpret a failure as proof against the cache axis unless the tested source also proves route invariance. Before the July 20 correction, this toggle changed the final long-prompt chunk boundary on GDN models even on an enabled-cache miss, so the storage A/B also changed recurrent-state numerics. Current source keeps the block-aligned boundary and configured token/layer quanta identical, suppresses only lookup/snapshot/registration/retention work, and has portable first-token, recurrent-state, and following-token parity coverage. The clean source-bound Strix Halo ROCm replacement arm subsequently passed all ten deterministic and eight sampled requests, including the formerly failing 2,432-token prompt, while every cache metric remained zero. Preserve both receipts: the pass closes this specific ROCm discriminator, while another backend or source revision still requires its own accelerator evidence.

Run graph lifecycle and byte-budget A/Bs separately

Start with graph-shaped eager versus native capture. Keep synchronization mode, both cache limits, model, corpus, request order, seed, sampling, concurrency, warmup, and memory configuration identical; change only rocm_graph_mode. The byte budget is an exact integer byte count, defaults to 1 GiB, accepts 64 MiB through 16 GiB, and has canonical environment name KILN_ACCELERATOR_ROCM_GRAPH_CACHE_MAX_BYTES. 

# rocm-graph-eager.toml
[server]
serving_profile = "experimental"

[accelerator]
rocm_synchronization_mode = "legacy_host_barriers"
rocm_graph_mode = "warmup_then_eager"
rocm_graph_cache_entries = 8
rocm_graph_cache_max_bytes = 1073741824

# rocm-graph-capture.toml: identical except this field
# rocm_graph_mode = "lazy_capture_replay"

kiln config --file rocm-graph-eager.toml
kiln serve --config rocm-graph-eager.toml
# Stop the first server, then repeat with rocm-graph-capture.toml.

After the capture arm passes parity and stability, a separate conservative budget-pressure arm may lower only rocm_graph_cache_max_bytes, for example to the 64 MiB minimum (67108864). That arm tests rejection, idle-owner eviction, and eager fallback; it is not a throughput target. Never raise the byte limit merely because a pause occurred. First require matching byte-budget rejections or evictions, accounting completeness, and sufficient live memory headroom. Entry/known-byte saturation should reclaim eligible idle owners before candidate allocation. If those cannot make room, fair active relief may retire the minimum selected exact geometries after settlement; one projected graph per active owner plus every live recurrent-state slot and continuity timeline must remain. After the settled warm pass, exact accounting, matching-device pressure, and atomic governor reservation should reject an inadmissible candidate before native capture. A defensive post-capture rejection is still possible if concurrent state changes. A candidate-alone byte or incomplete-accounting result makes that geometry non-capture-safe for the runner lifetime. Aggregate budget suppression clears only after owner or budget relief; reservation denial retries only after matching-device cached headroom is sufficient. Later matches take the typed eager fallback without another full warm/allocation pass. A memory_governor_selector_mismatch fails closed and is a configuration/topology fault, not evidence that the graph cache byte limit is too low.

The committed Strix Halo ROCm candidate provisions eight entries: one protected geometry for each of eight declared active owners and zero pre-reserved transition entries. Its typed launch file pins four ordinary decode rows, four staged-prefill slots, a 256-token/8-layer prefill quantum, a 512-token combined budget, and batching.actor_cycle_idle_ms=50. Health and trusted debug must attribute every field to the config file, and startup fails before model loading if the route-invariant prefill boundary no longer fits beside the effective decode width. Unused global headroom remains shared. At saturation, idle owners precede minimum fair-LRU active relief, which creates only the transition room then required while preserving one projected graph per active owner and every live recurrent-state slot. A same-binary A/B completed the identical first seven-wave sequence 25.3 percent faster at 12 than 24 entries despite lower active p50 SCLK; the smaller arm safely settled seven measured capacity transactions with zero fallback. That historical comparison supports a smaller graph population; it does not qualify the new eight-entry candidate. The rejected 32-layer mixed-load row stayed thermally contained but recorded fourteen nonthermal ITL outliers, so the current eight-layer quantum restores three scheduler turns inside each Qwen prefill. The guarded autoscale-off discriminator eliminated all fourteen classified ITL outliers and peaked at 88.75 C, but aggregate output fell to 12.748 tokens/second and p99 TTFT rose to 88.748 seconds. Require the remaining policy arms and its 30-minute soak before promotion, and require local evidence before changing it on another device. The soak terminates below 8 GiB MemAvailable and fails above 512 MiB swap growth. The soak, shorter ROCm mixed-load gate, and Vulkan soak share the independent 250 ms hard-limit-only thermal controller. It never sends SIGSTOP while accelerator work may be outstanding and fails closed at 97,000 millicelsius. Two exact ROCm serving rows proved that process-stop pacing can leave the device at 100-percent busy while the package cannot reach its resume gate, so any nonzero host_thermal_pacing_event_count now fails source-bound serving qualification. The mixed-load client and server share a 180-second request bound, expose a typed 90-second delivery-pressure observation window, and separately count thermal-paced, non-thermal attributed, and unexplained ITL gaps; all three populations must be zero under the current policy. Driver v11 requires a typed stable cooldown at a live-server idle boundary before and after every warmup or measured row and charges both waits to thermally sustainable phase time. Teardown preserves hard-limit monitoring through process exit. The runner returns only after eight consecutive 250 ms readings are at or below 75,000 millicelsius; the cooldown has a 180-second bound, explicit receipt metrics, and fails closed on timeout. A memory hard-stop still follows SIGTERM with SIGCONT as fail-safe cleanup for a legacy already-stopped group, but the current serving policy never initiates that state.

Driver v12 also bounds each guarded model-fingerprint worker with one cumulative model_fingerprint_read_mib_per_second schedule across both full integrity passes. Measured runs default to 256 MiB/s and accept 64 through 16,384 MiB/s; each limiter wait is at most 25 ms. The second read remains mandatory because it detects a concurrent same-length rewrite. The v2 thermal record binds the selected rate, worker implementation, Python executable, and both lifecycles. This protects provenance hashing only; it does not pace model upload or inference.

Driver v13 adds closed accounting for an explicit cooperative actor duty cycle. batching.actor_cycle_idle_ms accepts 0 through 60,000; zero is unpaced. A nonzero delay begins only after an actor cycle advanced model work and synchronous accelerator execution returned, polls control commands within 5 ms, and does not read a temperature sensor. Receipts record the configured source, measured-window wait count and elapsed seconds, process maximum, and final active state. The actor_cycle_idle_accounted gate fails contradictory or silently inactive pacing, while the independent thermal hard limit remains unchanged.

The first clean 256-token route-invariant development soak passed correctness and lifecycle gates but is retained as a performance counterexample: output throughput fell from 13.194 to 7.108 tokens/second versus the immediately prior accepted run. Treat that signature as a layer-yield/dispatch utilization investigation, keep the correct 256-token boundary, and run a same-binary A/B before any final ROCm endurance promotion.

Qualification compilation, runtime setup, measurement, and teardown have separate checked bounds. Current ROCm capture supports contiguous BF16 multi-row decode. A healthy batch route reports successful capture/replay, a retained shared width slot that is idle between cohorts, and zero kiln_rocm_graph_fallbacks_total{reason="multi_row_batch_unsupported"} delta. A positive value identifies a historical binary or a route outside the supported graph contract; it is not proof of VRAM rebalancing, and a graph-performance qualification must still fail.

For every new batch geometry, find exactly one event=rocm_graph_capture_parity_check. A passed event means the first graph launch matched its own eager warm hidden output, every recurrent and convolution tensor, and the current K/V rows. Inspect comparison_complete, compared_bytes, and duration_ms. A completed check also reports hidden_match; each first-mismatch layer field appears when that state family differs. An error reports the comparison failure instead. A failed, errored, or missing check on a claimed current-source capture is failure evidence. The runner must settle and restore state, discard the graph, disable graph execution, and report capture_failure before any contained eager retry; do not treat the eager completion as graph correctness. For durable evidence, require batched attempts and parity checks to reconcile to their outcome counters, successful batch admissions not to exceed passed checks, and a clean measured window to have zero failure/error with equal success/pass deltas. For cold_cache_host_round_trip or persistent_host_round_trip, inspect the paired event=rocm_graph_capture_host_transfer records. They identify each warm-pass upload by build-source file/line/column, dtype, elements and bytes per copy, copy count, and total bytes. The scope is thread- and device-local and keeps at most 32 unique sites per candidate; a source_file=bounded_site_overflow row aggregates the remainder. A site repeated on every attempt is a persistent forward path. A site present only on the first attempt can be a cold shape-cache fill, but actual capture and replay counters remain the authority. The event never includes prompt text, token IDs, tensor values, or allocation addresses.

A current binary does not upload ROCm broadcast shape metadata. Rank-eight shape and stride data is captured directly as a kernel value. If an attribution record names metadata construction in rocm_ops/index_select.rs, first compare the executable hash and source identity with the current receipt; on matching current source, treat the event as a regression and stop graph qualification.

Independently require kiln_rocm_graph_phase_telemetry_available 1. The phase label is exactly pre_candidate_headroom, candidate_warm, pre_native_reservation, native_capture, or rejected_candidate_cleanup. Compare calls, slow calls, total seconds, and maximum seconds; inspect kiln_rocm_graph_current_phase{phase} plus kiln_rocm_graph_current_phase_elapsed_seconds during the pause and kiln_rocm_graph_transient_candidate_bytes{kind="last|peak"} after measurement.

Do not equate capture success with cache retention. A kiln_rocm_graph_capture_outcomes_total{outcome="success"} increment means native instantiation and first launch succeeded, even if exact post-capture admission then safely rejected the candidate. kiln_rocm_graph_cache_admissions_total counts only the retained/replayable subset. Attribute their delta with entry/byte/accounting post-capture rejection counters and the corresponding closed fallback reason; it is not a capture failure.

opaque_native_object_count is a separate count of graph, executable, stream, and two event handles per retained entry. HIP does not expose their driver byte sizes, and allocator-pool slack is also outside retained_bytes. Compare the graph snapshot with live driver/governor memory; do not treat the byte-accounting total as whole-process VRAM residency.

Ordinary entry or byte pressure evicts deterministic least-recently-used idle owners as whole units. If those cannot make room at actual saturation, an exact-geometry miss uses deterministic fair-LRU active relief. The incoming candidate counts toward its owner's projected share; the most represented owner and then its oldest geometry are selected until the candidate fits, while every active owner retains one projected graph. Boundary pre_capture_active_fair_share preserves active slots, assignments, and continuity. A cache hit is never retired, and unused global headroom never triggers active eviction. Correlate a pause with the structured rocm_graph_cache_eviction event: a nonzero active_graph_only_owner_count identifies this prior-geometry path, while the boundary, removed counts, released bytes, and typed reason identify the exact transaction. Moderate pressure permits retained replay but blocks cache growth. Tight pressure evicts all eligible idle owners, permits an already-retained active-owner replay, and sends a miss to eager without capture. Critical or unavailable pressure settles and removes every graph, preserves active recurrent slot state, and uses eager execution only after cleanup proves safe. Rising budget_evictions, pressure_evictions, graph_cache_byte_budget, or tight_memory_pressure can therefore be expected evidence in the corresponding diagnostic arm; parity loss, unbounded plateaus, or cleanup quarantine are never expected.

Every eviction and rejected post-capture candidate follows pre-drop settlement, resource drop, then post-drop settlement. If the first settlement fails during cached eviction, the cache map remains intact. A safely settled and destroyed rejected candidate continues through its typed eager fallback. Only a rejected candidate whose pre-drop settlement fails falls into cleanup quarantine and retains possibly in-flight low-level handles until exit. Likewise, if a destructor, async free, or final settlement fails, quarantined_retained_bytes records the affected logical bytes and execution becomes cleanup-quarantined. Stop immediately: no eager retry is permitted, no successful reclaimed-byte event may be inferred, and the process must restart.

Diagnose native capture failure separately from rejected-candidate cleanup. A recoverable failure drains under synchronization reason capture_rollback while admission is still open and then restores logical recurrent state; only success of both proofs permits the capture_failure eager continuation. A failed settlement, failed logical rollback, or armed/unclassified guard exit publishes sticky STOP, uses error_recovery only for a post-STOP diagnostic drain, and requires restart even if that later drain succeeds. Treat quarantine as failure evidence, never as a normal fallback.

Tape switches do not isolate training or inference

Symptom

An old launch script sets KILN_USE_TAPE_*, ordinary inference unexpectedly avoids a fast path, a workload reports an unavailable tape/backward route, a step fails with an exact LoRA gradient error, or a profile shows frozen base-weight gradients or dWeight GEMMs.

Check
  • Inspect /v1/config at training.optimizer_support.workloads. That per-workload result, not a shell variable, is the static training-substrate authority.
  • Search the service definition for KILN_USE_TAPE_FORWARD, KILN_USE_TAPE_FLASH_ATTN, KILN_USE_TAPE_SDPA, KILN_USE_TAPE_LORA_ADD, and the four KILN_USE_TAPE_GDN* names.
  • Read the complete gradient error. A missing registered input indicates a disconnected use even if another clone reached the same leaf. Missing or unknown leaf IDs indicate graph/deposit drift, including a temporary slice ID that was not assembled into its original full leaf. Shape, backward dtype, or master-device mismatches indicate producer drift; NaN or infinity indicates numerical failure. A finite all-zero gradient is accepted, and a checkpoint range with no configured leaves must return an empty set.
  • Inspect tape inputs and profiler shapes. Only LoRA A/B are trainable model leaves. Embedding tables, base projection matrices, normalization weights, GDN gate parameters, MTP projections, and loss heads must be saved constants. Their backward routes must not emit a frozen-weight gradient; split Q/gate chunks must deposit under the original full A/B IDs and retain tape-aware reshapes.
  • On Metal, a synchronized full-gradient host scan at the optimizer boundary is the current correctness fallback until a native finite reducer is qualified. Profile it as an expected synchronization cost; do not bypass the check.
  • For an inference pause, use actor, prefill, synchronization, and memory metrics. A historical tape variable is not evidence that a tape scope exists.

Delete all eight names from launch scripts; they were removed without aliases or replacement fields. Kiln activates its required tape solely through an internal training scope. Ordinary inference opens no such scope and retains forward-only paths, including GDN chunkwise recurrence and CUDA’s weight-aware embedding lookup. Fix the producer named by an exact-gradient rejection. If a frozen gradient appears, route that operation through its frozen-input backward rather than filtering the result at the optimizer. No configuration bypass is supported.

  • A post-eval gate cannot safely rewrite a physically loaded adapter under the same name.
Fix

For adapter_active or adapter_loaded, call POST /v1/adapters/unload and retry. For adapter_revision_conflict, keep the intervening winner and resubmit against the current revision. Unload a gated same-name target or choose a versioned config.output_name. Hidden staging directories clean themselves up.
