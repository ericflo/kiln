Purpose
-------

Add profile-only instrumentation for the Vulkan GDN recurrent kernel path and
capture a live profile that splits the batch-3 recurrent step into CPU
extraction, staging, dispatch/wait, readback, and tensor materialization.

Source change
-------------

- Added `KILN_PROFILE_VULKAN_GDN_RECURRENT_KERNEL_STAGES=1`.
- The flag logs `kiln_profile_vulkan_gdn_recurrent_kernel_stage` rows from
  `dispatch_gdn_recurrent_step_with_options` and the default single-submit
  recurrent path.
- The instrumentation is disabled by default and Vulkan-only.
- CUDA and Metal source paths are untouched.

Interpretation
--------------

- The batch-3 recurrent bottleneck is not only shader dispatch. CPU-side state
  extraction/staging/readback/tensor rebuild is comparable to the dispatch/wait
  total.
- A124's direct packed-state upload/readback regressed because it still did
  per-token CPU layout conversion. A125 confirms that a useful follow-up needs
  to avoid the repeated host boundary, not just change the transfer format.
- The next credible Vulkan target is persistent/resident recurrent state across
  live decode steps or another design that keeps updated per-layer GDN state
  device-resident between tokens while preserving row ownership and scatter
  correctness.
- Smaller Q/K upload reductions inspired by the CUDA unexpanded-QK work are
  less likely to move live batch-3 throughput because input extraction/staging
  is small compared with recurrent state handling.
